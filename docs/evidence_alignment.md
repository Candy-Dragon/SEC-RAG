# SEC-RAG 前置证据约束设计：阶段 04—06

## 1. 文档状态

本文记录 SEC-RAG 当前讨论确定的目标设计，用于后续实现、实验复现、论文写作和汇报。

需要特别区分：

- 阶段 01—03 的检索、证据单元构建和完整性检查已经实现；
- 当前阶段 04—06 已实现信息需求标注、证据映射、覆盖汇总及带引用生成，并完成9题试运行；
- 本文记录设计契约；具体实现以当前代码和阶段输出为准，试运行不等于正式实验验证；
- 本文中的 JSON 和证据编号是结构示例，不是新的正式实验结果。

## 2. 方法目标与边界

当前 SEC-RAG 只研究生成答案之前的严格证据约束：

```text
完整问题
→ BM25 检索
→ 证据单元构建
→ 证据完整性检查
→ 信息需求标注与证据映射
→ 多证据覆盖汇总与回答边界
→ 依据获准原文证据生成带引用答案
```

当前方法不包含：

- 将原问题改写为多个新查询；
- 按 Q1、Q2 分别检索；
- 按 Q1、Q2 分别生成答案再拼接；
- 生成后的语义验证和自动修复；
- 使用社区参考答案参与生成；
- 开放域疾病识别和知识库自动路由。

## 3. 不可违反的全局原则

1. `original_question` 在所有阶段原样保留。
2. 信息需求标注只标记用户明确询问的内容，不创造新问题。
3. 症状、病史、既往治疗和患者条件属于上下文，除非用户明确询问，否则不能单独标成信息需求。
4. Q1、Q2 只是内部索引，不参与重新检索，不作为独立数据样本。
5. 所有证据判断均同时看到完整原问题和固定的信息需求标注。
6. 模型生成的 `supported_content` 只是证据用途说明，不能替代指南原文。
7. 阶段 05 和阶段 06 必须继续接收可追溯的原始 `evidence_text`。
8. 每个最终医学声明必须引用一个或多个获准 `evidence_id`。
9. 没有证据覆盖的部分必须明确说明证据不足，不能由模型使用外部知识补全。
10. 信息需求标注、证据映射和覆盖状态均是系统内部判断，不是临床金标准。

## 4. 阶段 01—03 的前置输入

### 4.1 阶段 01：共享 BM25 Top-N 检索

输入完整问题和受控疾病范围，返回排序后的指南片段、BM25 分数、指南文件、页码、章节和原文。

阶段 01 只表示文本检索相关性，不代表片段能够回答问题。

### 4.2 阶段 02：证据单元构建

模型只判断相邻原句如何组成证据单元。程序根据原句编号重建 `evidence_text`，不采用模型自由改写的指南文字。

### 4.3 阶段 03：证据完整性检查

逐条检查证据是否语义完整、是否被分页或分块截断、是否缺少必要前文。只有完整证据或能够从连续原文精确恢复的证据进入阶段 04。

阶段 03 只判断证据自身是否完整，不判断它是否适合回答当前问题。

## 5. 阶段 04：信息需求标注与证据映射

阶段 04 包含两个内部步骤，但保存在一个独立阶段记录中。

### 5.1 阶段 04A：信息需求标注

#### 目的

为原问题中用户明确提出的需求分配稳定编号，供后续证据归类和漏答检查使用。

这一步称为“信息需求标注”，不能称为问题分解、问题重写或子查询生成。

#### 输入

```json
{
  "question_id": "CMEDQA2_01976",
  "original_question": "咳嗽痰多有好几年了如何检查是不是肺癌？"
}
```

#### 输出

```json
{
  "original_question": "咳嗽痰多有好几年了如何检查是不是肺癌？",
  "information_needs": [
    {
      "need_id": "Q1",
      "source_span": "如何检查是不是肺癌",
      "description": "用户询问如何检查是否为肺癌"
    }
  ],
  "context_spans": [
    "咳嗽痰多有好几年了"
  ]
}
```

#### 约束

1. `source_span` 必须能够在原问题中精确定位。
2. 不强制把一条问题标成多个需求。
3. 总体需求已经包含细项时，不得同时生成父需求和重复子需求。
4. 只记录用户明确询问的内容。
5. 病史和症状作为上下文保存，不能自动变成新问题。
6. 后续阶段不能重新生成、合并或改写 Q1、Q2。

### 5.2 阶段 04B：逐证据映射

#### 目的

判断阶段 03 的每条完整证据能够支持哪项固定信息需求、具体支持什么、使用时必须保留什么条件，以及不能扩展成什么结论。

阶段 04 不判断某项需求最终是完整覆盖、部分覆盖还是没有覆盖。总体覆盖程度只能在阶段 05 汇总多条证据后判断。

#### 单次输入

```json
{
  "original_question": "咳嗽痰多有好几年了如何检查是不是肺癌？",
  "information_needs": [
    {
      "need_id": "Q1",
      "source_span": "如何检查是不是肺癌"
    }
  ],
  "context_spans": [
    "咳嗽痰多有好几年了"
  ],
  "evidence": {
    "evidence_id": "E002",
    "source_file": "肺癌诊疗指南.pdf",
    "source_pages": [20, 20],
    "section_heading": "影像学检查",
    "evidence_text": "胸部CT可有效检出早期周围型肺癌，并明确病变部位和累及范围。"
  }
}
```

#### 匹配证据输出

```json
{
  "evidence_id": "E002",
  "matched_need_ids": ["Q1"],
  "supported_content": [
    "胸部CT可以用于检出早期周围型肺癌，并明确病变部位和累及范围"
  ],
  "required_conditions": [],
  "unsupported_extensions": [
    "不能据此判断用户患有肺癌",
    "不能据此判断长期咳嗽痰多由肺癌引起",
    "不能据此确定胸部CT是该用户必须首先接受的检查",
    "不能据此给出完整检查顺序"
  ],
  "reason": "证据支持胸部CT在肺癌诊断中的作用，但未提供针对该用户症状的完整检查路径。"
}
```

#### 不匹配证据输出

```json
{
  "evidence_id": "E003",
  "matched_need_ids": [],
  "supported_content": [],
  "required_conditions": [],
  "unsupported_extensions": [],
  "reason": "证据主要描述肺癌分期和疗效评价，不能支持长期咳嗽患者如何检查是否为肺癌。"
}
```

#### 映射规则

1. `matched_need_ids` 为空表示该证据不进入回答范围，不再额外设置 `not_applicable` 标签。
2. 一条证据可以匹配多个真正独立的需求，但不能因为疾病主题相同而多选。
3. `supported_content` 必须是原始证据允许表达的最小范围，不能包含外部知识。
4. `required_conditions` 保存适用人群、临床阶段、病理类型、检查结果等必要条件。
5. `unsupported_extensions` 明确禁止从一般规则推导个体结论、检查顺序、诊断或治疗决定。
6. 危险因素不能自动解释为预防措施，相关性不能解释为因果关系，诊断信息不能解释为治疗建议。

## 6. 阶段 05：证据覆盖汇总与回答边界

### 6.1 目的

阶段 05 按固定 Q 编号汇总阶段 04 的证据映射，判断映射到同一需求的多条证据合起来能够回答该需求到什么程度，并生成阶段 06 必须遵守的回答边界。

阶段 05 不得：

- 重新识别或改写信息需求；
- 重新判断每条证据是否与需求匹配；
- 生成面向用户的答案；
- 用模型知识补全缺失证据。

### 6.2 程序预分组

程序先按照 `matched_need_ids` 将证据分组：

```json
{
  "Q1": ["E001", "E002", "E004", "E005"]
}
```

这一步不需要模型。

### 6.3 模型输入

阶段 05 必须同时接收：

- 完整原问题；
- 固定信息需求标注；
- 证据映射结果；
- 对应的原始指南 `evidence_text`。

模型概括的 `supported_content` 不能替代指南原文。

### 6.4 每项需求输出

```json
{
  "need_id": "Q1",
  "source_span": "如何检查是不是肺癌",
  "coverage": "partial",
  "evidence_usage": [
    {
      "evidence_id": "E002",
      "supported_content": "胸部CT在肺癌诊断和明确病变范围中的作用",
      "required_conditions": [],
      "used_for_generation": true,
      "reason": "直接支持肺癌诊断检查的一部分"
    },
    {
      "evidence_id": "E004",
      "supported_content": "痰液细胞学在中央型肺癌诊断中的作用",
      "required_conditions": [
        "中央型肺癌相关诊断场景"
      ],
      "used_for_generation": true,
      "reason": "只能作条件性说明，不能形成个体检查建议"
    },
    {
      "evidence_id": "E001",
      "supported_content": "肺癌存在多种影像学检查方式",
      "required_conditions": [],
      "used_for_generation": false,
      "reason": "内容过于概括，且主要内容已被更具体证据覆盖"
    }
  ],
  "supported_scope": [
    "可以说明胸部CT在肺癌诊断中的作用",
    "可以说明特定条件下痰液细胞学和支气管镜的作用"
  ],
  "missing_scope": [
    "不能判断长期咳嗽痰多是否由肺癌引起",
    "不能确定该用户是否需要启动肺癌专项检查",
    "不能给出检查先后顺序",
    "不能判断用户是否符合条件性检查的适用条件"
  ],
  "required_conditions": [
    "痰液细胞学必须保留中央型肺癌相关场景",
    "支气管镜必须保留进一步取材需求这一条件"
  ]
}
```

### 6.5 覆盖状态

每项需求只使用三种状态：

- `full`：现有证据能够回答该明确需求，没有实质性缺失范围；
- `partial`：现有证据能够回答一部分，但仍有明确缺失内容或未满足条件；
- `none`：没有证据能够支持该需求的任何可回答内容。

### 6.6 整体覆盖状态由程序派生

```text
所有需求均为 full
→ overall_coverage = full

至少一个需求为 full 或 partial，但并非全部 full
→ overall_coverage = partial

所有需求均为 none
→ overall_coverage = none
```

整体状态不能由模型自由选择。

### 6.7 生成边界

```json
{
  "generation_boundaries": {
    "must_answer_need_ids": ["Q1"],
    "must_state_insufficient_need_ids": ["Q1"],
    "allowed_evidence_ids": ["E002", "E004", "E005"],
    "must_preserve_conditions": [
      "痰液细胞学仅在中央型肺癌相关诊断场景下说明",
      "支气管镜仅在存在进一步取材需求时说明"
    ],
    "forbidden_content": [
      "判断用户患有肺癌",
      "判断长期咳嗽痰多由肺癌导致",
      "直接要求用户接受某项检查",
      "给出证据未支持的检查顺序",
      "机械罗列全部相关检查"
    ]
  }
}
```

## 7. 阶段 06：带逐句引用的最终答案

### 7.1 输入

阶段 06 接收：

- 完整原问题；
- 阶段 05 允许使用的原始证据；
- 每项需求的 `supported_scope` 和 `missing_scope`；
- 必须保留的条件；
- 禁止生成的内容；
- 固定生成提示词。

### 7.2 输出原则

1. 只回答 `must_answer_need_ids`。
2. `partial` 需求既回答证据支持部分，也说明缺失部分。
3. `none` 需求不生成医学结论，只说明当前证据不足。
4. 每个医学句子必须引用获准证据。
5. 不得重复同一事实、阈值、条件或建议。
6. 不得使用阶段 05 标记为 `used_for_generation=false` 的证据。
7. 模型可以自然组织语言，但不能超出 `supported_scope`。

### 7.3 示例输出

```json
{
  "answer": "胸部CT可用于肺癌诊断，并帮助明确病变部位和累及范围。[E002]\n\n在中央型肺癌相关诊断场景下，痰液细胞学可以作为无创诊断方法之一；在需要进一步组织学或细胞学取材时，支气管镜可以用于取材。[E004][E005]\n\n当前指南证据没有提供针对长期咳嗽、痰多患者的完整肺癌排查路径，也没有给出检查顺序，因此不能仅根据现有证据判断是否患有肺癌或确定应接受哪些检查。",
  "claims": [
    {
      "claim_id": "C1",
      "text": "胸部CT可用于肺癌诊断，并帮助明确病变部位和累及范围。",
      "evidence_ids": ["E002"]
    },
    {
      "claim_id": "C2",
      "text": "在中央型肺癌相关诊断场景下，痰液细胞学可以作为无创诊断方法之一；在需要进一步组织学或细胞学取材时，支气管镜可以用于取材。",
      "evidence_ids": ["E004", "E005"]
    }
  ],
  "insufficient_information": [
    {
      "need_id": "Q1",
      "statement": "当前指南证据没有提供针对长期咳嗽、痰多患者的完整肺癌排查路径，也没有给出检查顺序。"
    }
  ]
}
```

阶段 06 的输出就是当前 SEC-RAG 正式实验结果，不再执行生成后模型验证或自动修复。

## 8. 阶段 04 与阶段 05 的职责边界

```text
阶段 04：
原问题明确问了什么？
每条证据能支持哪个需求？
每条证据具体允许表达什么？
需要保留哪些条件？
不能扩展成什么？

阶段 05：
映射到同一需求的全部证据合起来能回答多少？
哪些证据允许进入生成？
哪些内容已被支持？
哪些内容仍然缺少依据？
阶段 06 必须回答、说明不足和禁止生成什么？
```

阶段 04 不输出 `full/partial/none`。阶段 05 不重新进行证据匹配，也不重新生成信息需求。

每条问题至少保存：

```text

03_integrity.json
04_evidence_need_mapping.json
05_coverage_boundary.json

```

每个模型阶段还必须保存：

- 使用的提示词路径和 SHA-256；
- 展开的 system/user messages；
- 模型原始响应；
- 结构化解析结果；
- 格式错误及重试；
- 模型名称、token 和延迟；
- 输入阶段路径和 SHA-256；
- 代码和配置版本。

## 10. 实现与验证顺序

1. 修改阶段 04A 的信息需求标注契约。
2. 修改阶段 04B 的逐证据映射契约。
3. 修改阶段 05，使其只能使用固定需求和映射结果，不重新识别需求。
4. 由程序派生 `overall_coverage`。
5. 修改阶段 06，只接收 `used_for_generation=true` 的原始证据。
6. 增加结构测试：原问题不变、`source_span`可定位、Q编号稳定、证据编号合法、条件传递完整。
7. 使用少量开发题重新运行并逐阶段人工检查。
8. 通过后再运行四种方法的同题对比。

## 11. 当前结论

阶段 04—05 应视为一个“证据—问题对齐与覆盖控制模块”的两个可审计子阶段：

```text
阶段 04：固定信息需求，并建立单条证据到需求的映射和使用限制。
阶段 05：按需求汇总多条证据，确定覆盖范围和最终回答边界。
```

保留两个阶段的主要原因是降低单次上下文复杂度、支持逐证据并发、便于定位错误和开展消融实验。其有效性仍需通过开发标注、基线比较和独立评价验证。
